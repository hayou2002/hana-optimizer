## 1 定位与管辖范围

本文件是**主工作台**（`<工作区>`；目录名随实例而异，本套文档以出厂默认名 `OH-WorkSpace` 为例叙述）的**户型图**，目的只有一个：**不让 OpenHanako 在使用过程中乱放文件**。

### 1.1 两套语言（本文件的认识论地基）

| 层 | 谁执法 | 例子 |
|---|---|---|
| **硬约束** | 平台内核/运行时**直接拒绝** | 挂载 capabilities、文件工具分级闸、ResourceIO 账本、App 进程 Permission Model |
| **软约定** | 文档/提示词/规范，靠执行者自觉 | 本规范、cron prompt、card-guide |

看一份规则前先问：它是平台内核会拒绝的，还是只是某段文字？**本文件写的是软约定，但处处标注了对应的硬约束在哪。**

### 1.2 管辖对象与前提

- **管辖对象**：`desk.home_folder` 所指目录（`<工作区>`）——**目录名随实例而异**，本套文档以出厂默认名 `OH-WorkSpace` 为例叙述。
  > 名字只是当前值：`OH-WorkSpace` 是**出厂默认目录名**（安装包曾硬编码、删除反复重建，旧 bug #1906）；真机制是 `desk.home_folder`，每个 Agent 可自定义。改名/搬家后，本文件节点路径按新值重解析。**读到文中任何具体目录名/数字时，先按「环境对位」核对你的现场，不照搬。**
- **前提（硬）**：主根必须是 `studio-mounts.json` 里 `status=active`、`provider=local_fs`、`capabilities` 含 `list+read+write` 的挂载；否则 ResourceIO 层连读都拒。

### 1.3 「AI 乱放文件」的真实风险面

文件工具按 realpath 分级（详见 §6.3）：**工作区挂载根内 = FULL**；`{HANA_HOME}` 整体（含 `skills/`、`user/`、`session-files/`）= **READ_ONLY**；`auth.json` 等 = **BLOCKED**；删操作需 FULL。

**结论**：AI 无法在平台区乱放文件——真实风险面**只在挂载根以内**，本规范也只需管好挂载根。但挂载根以内有两个**不受本规范直接控制、却天天在写**的当事人：**平台内核**（§2.2 常驻户）与**定时任务**（§9）。

## 2 顶层结构

### 2.1 六格（用户与 Agent 的工作区）

| 顶层 | 角色 | 住什么 | 时钟 | 平台内核可动性 |
|---|---|---|---|---|
| `projects/` | 正在做的活 | 本地工作台项目 | 无 | 受保护 |
| `storage/` | 仓库·永久区 | `docs/`・`存底/`・`tools/` | 无 | 受保护 |
| `inbox/` | 前门 | 手动拖入 + 说不清归属的成果 | 周裁决，>14 天红标 | **进**可自动归类（`rootStrayAuto`），**出**只经裁决 |
| `_temp/` | 时钟区 | 截图/数据/一次性/导出/jobs/反悔区/检查点 | **各类自带时钟** | 可自动出清 |
| `个性化/` | 保护·只看不碰 | `资料/`、`agent提示词/`、`联动/` | 无 | **protectedPaths** |
| `.server/` | 隐藏系统件 | 工作区级系统件 | 无 | **protectedPaths** |

> 点开头目录（`.server`、`.cache` 类）被扫描器**直接跳过**——需要就显式登记，别指望时钟。

### 2.2 平台常驻户（平台内核硬编码，非用户选择）

平台自己会在工作区根**自动创建并写入**，名字由平台内核算定、改不了：

| 常驻户 | 触发时机 | 内容 | 铁律 |
|---|---|---|---|
| `OH-Works/` | 用日记 / 截图 / 会话产物 / 巡检时 | `截图/`(Screenshots)、`日记/`(Diary)、`产物/`(Outputs)、`{Agent名的巡检}/patrol-log.md`，及约定的 `Cards/` | kind 白名单恰为三类；**AI 只看不碰** |
| `OH-媒体库/` | 生成图/视频/语音完成时 | 媒体出生即从会话缓存**搬来** | **永不自动清理**；可在设置改址 |
| `魔术卡/` | 钉住一张卡片时 | `魔术卡/{标题}/` 自包含文件夹 | **任何清理器不得删**；搬动即断链 |

三条纪律：**不搬、不改名、不并入**。它们的 `identityContract` 只认这一处路径——一旦被 `rootStray` 搬走，被钉的卡与媒体库资产会指向死路径。这些目录在用户视图里被平台内核**隐藏**（辨识出是平台保留名，不是整理对象）。

> 平台常驻户在首次使用对应功能前可能尚未出现，一旦首次用日记/生图/钉卡即自动生成。**故必须提前写进白名单**——这是唯一"现在不收编、将来必然违规"的点。

### 2.3 写入者登记表

「谁负责写」不再只写"会话/用户"。**每个写入者都要签字**：

| 写入者 | 会往哪写 | 受什么约束 |
|---|---|---|
| 主会话（该 Agent） | 六格 + 挂载外域 | 四问决策树 + 双写纪律 + 交付登记 |
| 子 agent | 继承主会话落点 | **继承**主会话的双写纪律与四问声明（无独立身份） |
| cron 会话（定时治理任务） | 检查点、`开发反思.md`、按 prompt 内嵌白名单 | **prompt 是"预先签发的落点授权书"**：内嵌白名单/映射表与本文件同批修订（§9） |
| 平台内核 | 平台常驻户（§2.2）、`trash` | 平台内核硬编码，**不在本规范管辖**，只承认其存在 |
| 浏览器 / 计算机工具 | `_temp/截图` 或指定落点 | 同主会话 |

## 3 逐层说明

### 3.1 `projects/` — 正在做的活
每项目一目录；最低合规件 `项目索引.md`（**必须**，缺件只提醒不代写）；迭代史用 **git tag**；项目内 `.gitignore` **必含** `dist/ build/ node_modules/ *.vsix`（§9）。**中间物与成果分家**（§5.1）。项目内部结构详见 **03**。

### 3.2 `storage/` — 仓库（永久区，三格）
见 §2.1 表；`存底/` 须过存底资格闸（**定义见设计蓝图 §3**）；`tools/` **仅 KB 级文本脚本**（>10MB 拦下）。**大体积中间态**（npm 工程、解包源码、`node_modules`）**不在三格准入内**——户口见 §9。

### 3.3 `inbox/` — 前门
只进两类（拖入 / 说不清）。出口白名单五处：projects / storage / `_temp/一次性` / 反悔区 / 归档位。裁决细则见 **05**。

### 3.4 `_temp/` — 时钟区
根不留散文件；时钟只作用于 `_temp` 子树；反悔区由批次时钟管辖（04）。

### 3.5 `个性化/` — 保护·只看不碰
入 `protectedPaths`；`资料/备考/` 归类只建议不自动动；`联动/*` 仅记录新路径等确认。

### 3.6 `.server/` — 隐藏系统件
入 `protectedPaths`；仅登记与报告。

### 3.7 卡片与卡包

- **钉住的卡**由平台搬进 `魔术卡/`，**AI 不参与**（常驻户铁律）。
- **未钉的铸造卡**（file source）落 `projects/{名}/cards/`（项目内）或 `storage/docs/`；**不要撒在工作区根**。
  > 平台 card-guide 让写 `OH-Works/Cards/`，但**公开仓库无出处**，平台内核的 OH-Works kind 白名单只有 `截图/日记/产物`——该路径属**历史软约定，不推荐新写入**；与 §2.2 常驻户铁律冲突时以本条为准。
- **卡包媒体**一律进包内 `assets/`，用相对路径引用；`data:` URI 只留给极小装饰图。
- **`packageAssets`** 声明"缺它就展不出"的文件；**`show_card.assets`** 只选本次要用的。两者都是**硬契约**（缺文件 / 非法形态直接报错）。

### 3.8 交付铁律

**只在文本里报路径不算交付。** 成果要进会话，走 `stage_files` / `resources.stage` 登记为 SessionFile——落工作区的副本才是家，两份一致由双写纪律保证（§7）。

## 4 新文件决策树（落点唯一入口）

```
Q0 名字撞平台保留名（OH-Works/OH-媒体库/魔术卡）？ ──是──▶ 就地不动，不进任何归位流程
   │否
Q1 是本地工作台的活吗？ ──是──▶ projects/{名}/
   │否
Q2 属于运维台账 / 产品线资产吗？ ──是──▶ 外部总部（已挂载：<外部根>）
   │否                    （注意：**不受本规范管辖，但受挂载授权管辖**——须在 studio-mounts.json 且带 write）
Q3 是有寿命的临时件吗？ ──是──▶ _temp/{对应时钟子目录}/
   │否
Q4 其余一切 / 说不清 ──▶ inbox/（等裁决）
```

- **顶层白名单制**：白名单（六格 + §2.2 常驻户）外落笔视为违规。
- Agent 生成新文件时**同轮声明走的是第几问**。
- 落点禁区与归类表**必须同源**（同源校验会拒绝落点在带时钟目录/受保护顶层的归类表）。

## 5 作业区三层与生命周期

### 5.1 作业区三层

| 层 | 位置 | 住什么 | 时钟与清理 |
|---|---|---|---|
| 平台会话区 | `%USERPROFILE%\.hanako\session-files\{会话哈希}\` | Hana 登记的会话文件 | **平台自管**：命名式 `{原名}_{ts36}_{hex8}.{ext}`；**身份是 SessionFileId，路径只是定位器**；冷会话缓存 72h 自清 |
| 作业区 | `_temp/jobs/{YYYYMMDD}-{会话slug}/` | 纯可弃中间产物 | 7 天；经孤本检索放行后入反悔区 |
| 成果之家 | `projects/` `storage/` `个性化/` | 交付物 | **时钟物理碰不到** |

**双写纪律**：开工即同时建中间产物区与成果之家；每轮交付声明"成果已落在 X，中间物在 Y 待时钟"。**不靠记性，靠结构。**

> 沙箱开启时命令的 `%TEMP%`、npm/pip 缓存被平台重定向到 `{HANA_HOME}/.ephemeral/win32-sandbox-env/*`（平台自管）。**Agent 自己产生的中间物不要靠 Temp，一律点名写 `_temp/jobs/{当日}-{会话slug}/`**，否则既不在工作时钟射程内、也不在治理视野内。

### 5.2 生命周期表（人读快照 · 非权威）

> **数值唯一源 = `rules.json`**（§6.1）；本表只是人读快照，机器以规则源为准。

| 子目录 | 天数 | 出清方式 |
|---|---|---|
| `_temp/截图` / `_temp/一次性` | 7 | 到期入反悔区 |
| `_temp/数据` | 14 | 同上 |
| `_temp/导出` | 30 | 同上 |
| `_temp/jobs` | 7 | 孤本检索放行后入反悔区 |
| `_temp/检查点` | 保 10 份 | pruneCheckpoints |
| `_temp/反悔区` | 批次 14（推荐）/ 30（激进） | 到期 purge |
| `_temp` 内日志 | 3 | pruneLogs |
| `storage/存底` | 保 7 份 | pruneBackups |
| `storage/tools` 闲置 | 90 | idleTools（仅建议） |

> **截图的两种来源（勿混）**：① **工具直接产出**（浏览器/计算机截图）→ 写 `_temp/截图`，走 7 天时钟；② **根上散落的图片** → 由 `classify` 自动归入 `inbox`。规则硬约束「带时钟目录永不做自动落点」，故自动归家只能进 inbox——两者不冲突，是不同来源。

### 5.3 回收通道（完整规则归 04）★

**清理与回收的完整规则归 04**（三法域、四类对象、反悔区 / trash / 历史库）。此处只记一条边界：**工作区反悔区**在 `_temp/反悔区/{YYYYMMDD}/`，按 `.manifest.jsonl` 原路放回（**04 管辖**）；平台 `trash` 与 `file-history` 是本体物件，归 **02** 登记。

> 注：`user-guide` 里"改删前整份复制到 checkpoints/"的文件备份机制**已退役**，现存 `checkpoints/` 只剩一次性启动清理。**别承诺"有文件备份可回滚"**——撤销只靠反悔区 + 历史库。

## 6 三源、保护清单与边界

### 6.1 三个权威源（不再有"rules.json 唯一源"）

| 管什么 | 唯一来源 | 路径 |
|---|---|---|
| **默认工作区根** | Agent 配置 | `agents/{id}/config.yaml` → `desk.home_folder` |
| **清理细则**（生命周期/白名单/保份数/落点/风险档/熔断/豁免） | 工作区 `rules.json` | `<根>/.optimize/rules.json` |
| **平台默认落点** | 平台内核硬编码 | bundle 代码（`OH-Works`/`OH-媒体库`/`魔术卡`，改不了） |

> `rules.json` 里的 `workspaceRoot`（常见为历史遗留值 `<外部根>`）是**陈旧残留**——根以 Agent 配置（`desk.home_folder`）为准。按旧表述去"改机器源"会改在遗物上。

### 6.2 保护清单与禁区

- **顶层白名单**：`projects` `storage` `inbox` `_temp` `个性化` `.server` ＋ 平台常驻户（§2.2）
- **protectedPaths**：`个性化` `storage` `projects` `.server`（＋ 平台常驻户）
  > ⚠️ **`inbox` 不在 protectedPaths**——它是归类落点，靠「无时钟 + 出口白名单」约束保护，这是原设计意图（inbox 不是 protectedPaths，归类落点需要能进它）。蓝图附录 A 写的五项含 inbox 是**笔误**，以规则源为准。
- **rootStray 豁免**：平台常驻户 ＋ 约定名根文件（`AGENTS.md` / `README.md` / `.gitignore`）
- **落点禁区**：`..` / 绝对路径逃逸 / 受保护顶层 / 带时钟目录 → 拦
- **同源校验（硬）**：`rules.json` 落盘前过同源校验——`logs.dir` 必须在 `_temp` 内；**归类落点命中带时钟目录/受保护顶层即整次拒写**

### 6.3 读写边界（文件工具分级闸，硬）

| 档 | 范围 |
|---|---|
| **FULL**（读写删） | 工作区挂载根内 |
| **READ_WRITE** | `{HANA_HOME}/{channels,logs,uploads,.ephemeral}`；agent 的 `memory/sessions/desk/activity/avatars` |
| **READ_ONLY** | `{HANA_HOME}` 整体（含 `skills/` `apps/` `user/` `session-files/`）；agent 的 `AGENTS.md`/`config.yaml`/`identity.md` |
| **BLOCKED** | `auth.json` `models.json` `added-models.yaml` `crash.log`、`browser-data`、`playwright-browsers` |

写需 ≥READ_WRITE，删需 FULL，stage 需 ≥READ。**平台区由平台运行时执法，本规范无需重复设防；扩展增删走 `extension_manager`，不 rm 目录。**

### 6.4 改动纪律

文档 / `rules.json` / cron prompt **三处，任一处变更必须同轮改其余两处**。归类表（扩展名 → 落点）不在本文件抄写，以 `rules.json` 为准（防抄本漂移）。

## 8 目标态与现场对照

| 顶层 | 目标态 | 现场可能的情况 | 备注 |
|---|---|---|---|
| 六格 | 见 §2.1 | 未建齐，或已是另一套成熟结构 | 以现场实测为准（先做「环境对位」） |
| **平台常驻户** | 收编白名单 | 首次使用对应功能前可能尚未出现 | **迁移/初始化前先写进白名单** |
| 历史遗留目录（如 `_tools/`、`data/`） | 逐步收拢 → 六格对应位 | 可能仍在用 | 不硬搬；混入的大体积中间态另行升格 |
| 本规范集自身 | 建议复制进 `storage/docs/` | 可能尚在别处 | 文档集须落在某个挂载内 |

> **收敛原则**：只补缺口、不硬搬；结构落差大时按自己的节奏一次做完，不做逐目录手工迁移。

## 9 部署与迁移检查清单

> 首次部署（或从旧结构迁移）时逐条核对；条目为建议，按现场取舍。一次真实核对的历史记录见**附录 D**。

1. **规则表先就位**：`rules.json` 的 `rootWhitelist`/`protectedPaths` 须包含**平台常驻户**（否则首件落地即被 `rootStray` 搬走）；`protectedPaths` 不含 `inbox`、`classify→inbox` 均为**设计意图**，照规则走即可。
2. **定时任务与文档同批**：治理任务 prompt 内的白名单/映射表须与本规范同批修订（详见 08 §1、§5）——它是挂载根内唯一的每日自动写入者。
3. **旧结构收拢**：现场如有旧目录（`_tools/`、`data/` 类），逐步收拢至六格对应位；不硬搬、不新增写入旧位。
4. **大体积中间态升格**：混入的 npm 工程、解包源码——升格 `projects/` 或显式豁免时钟。
5. **本规范集可自持**：按需把 `references/rules/` 复制进 `storage/docs/`。
6. **凭据纪律**：不把凭据写进命令行/文件名（`.ephemeral` 日志面归 02）。

## 附录 B · 挂载与法域

- 挂载（`studio-mounts.json`）：主工作台为 `<工作区>`，其余外部根为 `<外部根>`，均登记 `path` 与 `list/read/write`。
- **只有挂载法域才谈得上治理**；`.hanako` 本体根不在其中。注意：本体 `channels/logs/uploads/.ephemeral` 虽在 READ_WRITE 档（§6.3），但 02 红线禁止 Agent 主动删——**能写 ≠ 该删**。

## 附录 D · 机器层修订对照（旧 → 新）

> **用途**：记录一次「把纸面规则与机器执行规则对齐」的核对过程（**早期实例存档，非规范本体**）。新实例如需同类核对，可作方法参考；先做「环境对位」，勿照搬现值。

### D.1 rules.json 逐字段核对（示例：某实例实测）

路径：`<根>/.optimize/rules.json`

| 字段 | 现值（实测） | 判定 | 动作 |
|---|---|---|---|
| `workspaceRoot` | `<外部根>`（历史遗留值） | **陈旧残留**（根以 Agent 配置 `desk.home_folder` 为准，此值仅兜底） | 可清理 |
| `rootWhitelist` | 六项 | **缺平台常驻户** | ★**必须加** `OH-Works` `OH-媒体库` `魔术卡` |
| `protectedPaths` | 四项（无 inbox） | **正确**（inbox 故意不保护） | 不改；★加平台常驻户 |
| `tempLifecycle[待裁决]` | `maxAgeDays: 0` | **无害占位**（0 = 不参与时钟） | 可清理 |
| `tempLifecycle[反悔区]` | `maxAgeDays: 0` | 同上 | 可清理 |
| `classify`（png/jpg/js…） | `autoHome → inbox` | **设计意图**（带时钟目录永不做落点） | 不改 |

> 结论：`rules.json` 只有**一处必须改**（白名单/保护区加常驻户，防未来误判），其余是残留或本就正确。

### D.2 归类任务 prompt 对齐（示例：旧 → 新）

| 项 | 旧（现 prompt 内嵌） | 新 |

### D.3 执行前提与回滚

- `rules.json` 由 Agent 现场读写 `<根>/.optimize/rules.json`；cron prompt 走 `automation` 工具。**cron 不直接改文件。**
- 改动前记录现值（先 read `rules.json` / `automation list`），可回滚。
- 顺序：先改 `rules.json`（白名单/保护区）→ 再改 cron prompt → 两处与本文件**同批**（§6.4 三处同改纪律）。
- **记录性质**：以上为一次核对的方案存档（**非执行记录**）；如你的实例类同，照此思路逐项核对。
